# house_kgz — backend

REST API мобильного приложения-агрегатора недвижимости.

**Стек:** Python 3.12 · Django 5 · Django REST Framework · PostgreSQL 16 · Redis 7 ·
Celery (+ Beat) · MinIO/S3 · Docker Compose.

Каркас проекта (настройки, единый формат ошибок, пагинация, документация API,
health-check) плюс доменные модели, необходимые сидеру демо-данных:
пользователи, каталог объявлений и кошелёк. API-эндпоинтов каталога пока нет —
они появятся в фазах 1–6 ТЗ ([flutter_app/BACKEND_TZ.md](../flutter_app/BACKEND_TZ.md)).

## Быстрый старт (Docker)

```bash
cd backend
cp .env.example .env      # при необходимости поправьте значения
make up                   # соберёт образы и поднимет всё окружение
```

Что поднимается:

| Сервис        | Адрес                      | Назначение                          |
|---------------|----------------------------|-------------------------------------|
| `web`         | http://localhost:8000      | Django + DRF                        |
| `db`          | localhost:5432             | PostgreSQL 16 (healthcheck)         |
| `redis`       | localhost:6379             | кэш + брокер Celery                 |
| `celery`      | —                          | воркер, очередь `default`           |
| `celery-beat` | —                          | планировщик (django-celery-beat)    |
| `minio`       | http://localhost:9001      | консоль S3-хранилища (minioadmin)   |
| `minio-init`  | —                          | разово создаёт бакет и открывает его |

Миграции применяются автоматически при старте `web` (`RUN_MIGRATIONS=true`).

Проверить, что всё живо:

```bash
curl http://localhost:8000/api/v1/health/
```

Ответ: `{"status": "ok", "db": true, "redis": true}` (503, если БД или Redis недоступны).

Дальше:

```bash
make superuser            # создать администратора
make seed                 # демо-данные по прототипу Flutter
make seed ARGS=--flush    # то же, но сначала очистить доменные таблицы
make logs                 # логи (make logs SERVICE=celery — по одному сервису)
make down                 # остановить
```

## Соглашения API

**Версионирование.** Всё API живёт под `/api/v1/` (`URLPathVersioning`, `DEFAULT_VERSION="v1"`).

**Аутентификация.** JWT (`djangorestframework-simplejwt`) — заголовок
`Authorization: Bearer <access>`. По умолчанию права — `AllowAny`;
каждая вьюха обязана объявлять `permission_classes` явно.

**Пагинация.** Курсорная, по умолчанию 20 объектов, максимум 100
(`?page_size=50&cursor=...`). Формат ответа:

```json
{"results": [], "next": "https://.../?cursor=cD0y", "previous": null, "count": 128}
```

Курсор сортирует по `-created_at`, поэтому пагинируемые модели должны наследовать
`TimeStampedModel` (или переопределять `ordering` у своего класса пагинации).

**Ошибки.** Любая ошибка приходит в одном формате:

```json
{
  "error": {
    "code": "validation_error",
    "message": "Проверьте правильность заполнения полей.",
    "details": {"price": ["Обязательное поле."]}
  }
}
```

| HTTP | code                    | Когда                                    |
|------|-------------------------|------------------------------------------|
| 400  | `validation_error`      | не прошла валидация                      |
| 401  | `authentication_failed` | нет/протух токен                         |
| 402  | `insufficient_funds`    | не хватает средств (`InsufficientFundsError`) |
| 403  | `permission_denied`     | нет прав                                 |
| 404  | `not_found`             | объекта или адреса нет                   |
| 409  | `conflict`              | дубликат / гонка (`ConflictError`)       |
| 429  | `throttled`             | превышен лимит запросов                  |
| 500  | `server_error`          | непойманная ошибка (пишется в лог)       |

## Конфигурация мобильного клиента

Всё, что должно меняться без релиза приложения, живёт в админке и отдаётся
четырьмя эндпоинтами (все `AllowAny`):

| Эндпоинт | Что отдаёт |
|---|---|
| `GET /api/v1/app/config/?platform=android&version=1.0.3` | версии, `force_update`, ссылку на стор, режим обслуживания, фича-флаги, константы, ссылки на документы |
| `GET /api/v1/app/onboarding/` | активные слайды онбординга по порядку |
| `GET /api/v1/app/pages/{slug}/` | `terms`, `privacy`, `about`, `faq`, `support` — markdown и версия текста |
| `POST /api/v1/support/tickets/` | обращение в поддержку, не более 5 в час на аккаунт или IP |

- **`force_update`** считается сравнением семвера, а не строк: `1.0.9 < 1.0.10`.
  Если клиент не прислал `version`, принудительное обновление не включается.
- **Кэш** — Redis, 15 минут (`apps/common/services.py`). Инвалидируется сигналами
  `post_save`/`post_delete` на `AppConfig`, `OnboardingSlide`, `StaticPage`,
  поэтому правка в админке видна сразу.
- **ETag.** Ответы `/app/*` содержат `ETag` (md5 тела) и `Cache-Control: public, max-age=900`.
  Клиент шлёт `If-None-Match` и получает `304` без тела — конфиг дёргается на каждом старте.
- **`StaticPage.version`** увеличивается вручную при правке текста соглашений: по ней
  запрашивается новое согласие пользователя (задача 9.2 ТЗ).
- **Константы** (`topup_bonus_rate`, `promotion_price_per_day`, `max_photos`,
  `max_videos`, `free_active_listings`) читаются клиентом из конфига, а не хардкодятся.

Письма о новых обращениях уходят на `SUPPORT_NOTIFY_EMAILS` (или на `ADMINS`)
Celery-задачей `common.notify_support_ticket`; если брокер недоступен, письмо
отправляется синхронно.

## Аутентификация: телефон + SMS-код → JWT

| Метод | Путь | Что делает |
|---|---|---|
| POST | `/api/v1/auth/otp/request/` | `{"phone", "purpose"}` → `{"expires_in": 300, "resend_after": 60, "is_new_user": bool}` |
| POST | `/api/v1/auth/otp/verify/` | `{"phone", "code", "name"}` → `{"access", "refresh", "user", "is_new_user"}` |
| POST | `/api/v1/auth/pro/register/` | `{"phone", "name", "password", "iin", "whatsapp"}` → `{"expires_in", "resend_after"}` |
| POST | `/api/v1/auth/password/login/` | `{"phone", "password"}` → та же пара токенов, только для `is_pro` |
| POST | `/api/v1/auth/refresh/` | стандартный `TokenRefreshView` SimpleJWT |
| POST | `/api/v1/auth/logout/` | `{"refresh"}` → `204`, токен уходит в blacklist |

- **Код** — 4 цифры из `secrets.randbelow`, живёт 5 минут. В БД лежит только хеш
  (`django.contrib.auth.hashers`). Открытый код не попадает ни в ответ API, ни в логи —
  единственное исключение — `ConsoleSmsProvider` при `DEBUG=True`.
- **Тестовые номера.** При `DEBUG=True` или для номеров из `OTP_TEST_PHONES` код всегда
  `OTP_DEBUG_CODE` (`0000`) и SMS не отправляется — для ревью в сторах и автотестов.
- **Лимиты** (`apps/users/throttling.py`, счётчики в Redis): 1 код в минуту и 5 в час на
  номер, 20 в час на IP. Превышение — `429` с `details.retry_after`.
- **Неверный код**: `400`, сообщение «Неверный код», `details.attempts_left`. После пяти
  неудачных попыток код сжигается (`is_used=True`) — нужен новый.
- **SMS** уходит Celery-задачей `users.send_otp_sms` (3 ретрая). Провайдер выбирается
  настройкой `SMS_PROVIDER`: `console` (лог) или `http` (POST на `SMS_API_URL`,
  таймаут 10 с, 2 ретрая с экспоненциальной задержкой).
- **Токены**: access 15 минут, refresh 30 дней, ротация с занесением старого refresh
  в blacklist (`rest_framework_simplejwt.token_blacklist`).
- **Чистка**: Celery Beat раз в сутки (03:15) запускает `users.purge_old_otp_codes` —
  удаляет коды старше `OTP_RETENTION_DAYS` (7 дней).

### Регистрация исполнителя (pro)

Экран `pro_signup_page`: телефон, WhatsApp, имя, пароль, ИИН.

1. `POST /auth/pro/register/` — валидирует ИИН (`apps/users/validators.py`: ровно 14 цифр)
   и пароль (`AUTH_PASSWORD_VALIDATORS`, минимум 8 символов), создаёт **или дозаполняет**
   аккаунт с тем же телефоном (второго не появляется), сохраняет `whatsapp_phone`
   и высылает код с `purpose=pro_register`. `is_pro` пока остаётся `False`.
2. `POST /auth/otp/verify/` с `purpose=pro_register` — включает `is_pro=True`
   и заводит кошелёк (`billing.Wallet`, идемпотентно).

`409 conflict` возвращается, когда ИИН занят другим аккаунтом или у номера уже указан
другой ИИН. ИИН защищён и на уровне БД: `UniqueConstraint` с условием `iin != ""`.

Вход по паролю (`/auth/password/login/`) доступен только подтверждённым исполнителям.
Любая неудача — `401` с одним и тем же текстом «Неверный номер телефона или пароль»,
чтобы по ответу нельзя было проверить, зарегистрирован ли номер. Лимиты: 10 попыток
в час на номер и 30 — с одного IP.

## Фильтрация и поиск

`ListingFilterSet` ([filters.py](apps/catalog/filters.py)) подключён и к `/listings/`,
и к `/listings/count/`. Мультивыбор передаётся через запятую и внутри параметра
объединяется по ИЛИ, разные параметры — по И.

| Параметр | Поведение |
|---|---|
| `search` | полнотекстовый поиск (см. ниже) |
| `kind`, `district`, `seller_kind`, `series` | мультивыбор: `?kind=apartment,house` |
| `city`, `builder` | по слагу |
| `rooms` | мультивыбор; `5` означает «5 и более» |
| `area_min`, `area_max`, `area_ranges` | `?area_ranges=35-45,65-75`; диапазоны — по ИЛИ между собой **и по ИЛИ с ручной вилкой** |
| `price_min`, `price_max`, `currency` | сравнение по `price_usd`; при `currency=KGS` порог конвертируется в доллары |
| `floor_min`, `floor_max`, `not_first_floor`, `not_last_floor` | `not_last_floor` — `floor < floors` |
| `is_secondary`, `below_market`, `red_book`, `has_video` | флаги; `has_video` — подзапрос `Exists` |

`GET /api/v1/listings/count/` принимает те же параметры и отдаёт `{"count": 137}`
для кнопки «Показать N объектов»: без пагинации и сериализации, только `COUNT(*)`.
Результат кэшируется на 60 секунд по хешу нормализованной строки параметров
(порядок параметров и `page_size`/`cursor`/`ordering` на ключ не влияют).

### Полнотекстовый поиск

Поле `Listing.search_vector` собирается из района (вес A), адреса и застройщика (B)
и описания (C) с конфигурацией `russian`. Обновляется тремя путями: задачей
`catalog.update_listing_search_vector` после публикации, действием «Опубликовать»
в админке (одним `UPDATE` на пачку) и командой полного пересчёта:

```bash
docker compose exec web python manage.py rebuild_search_index --active-only
```

Запрос идёт через `SearchQuery(search_type="websearch")` с сортировкой по `SearchRank`;
если точных совпадений нет — включается поиск по триграммам (`pg_trgm`, порог 0.3),
чтобы «технпарк» с опечаткой находил «Технопарк». При активном `search` и без явного
`?ordering=` выдача сортируется по релевантности.

> Всё это — возможности PostgreSQL. На SQLite (локальный прогон тестов) поиск
> деградирует до `icontains`, а два теста про триграммы и ранжирование помечены
> `skipif` и выполняются только на Postgres.

### Валюты

`ExchangeRate` хранит историю курсов. Celery Beat в 09:00 по Asia/Bishkek запускает
`catalog.fetch_exchange_rates`: тянет XML НБКР, сохраняет курс USD/KGS, сбрасывает
кэш и пересчитывает `Listing.price_usd` одним `UPDATE`. Если источник недоступен —
задача пишет предупреждение в лог и оставляет прошлый курс, не падая. Пока курсов
нет вовсе, используется `FALLBACK_USD_KGS_RATE`.

`price_usd` — денормализация: заполняется в `Listing.save()` и пересчитывается
пачкой при обновлении курса. Все фильтры и сортировки по цене идут по нему,
иначе объявления в сомах выпадали бы из ценового диапазона.

## Создание и жизненный цикл объявления

Флоу «Продать недвижимость» из Flutter: `ad_form_page` → `ad_photos_page` →
`ad_video_page` → `ad_promo_page`.

| Метод | Путь | Что делает |
|---|---|---|
| POST | `/api/v1/listings/draft/` | получить или создать черновик (один на пользователя) |
| PATCH | `/api/v1/listings/{slug}/` | частичное сохранение формы, любое подмножество полей |
| POST | `/api/v1/listings/{slug}/publish/` | на модерацию (или сразу в эфир для доверенных) |
| GET | `/api/v1/users/me/listings/?status=` | «Мои объявления» со статистикой |
| POST | `.../archive/`, `.../restore/`, `.../mark-sold/`, `.../bump/` | действия владельца |
| DELETE | `/api/v1/listings/{slug}/` | мягкое удаление |

- **Черновик живёт на сервере**, а не в памяти приложения: заполненная форма
  не теряется при закрытии приложения и доступна с другого устройства.
  Дефолты те же, что в `AppState` Flutter (`new_building`, 1 комната, 1/1 этаж,
  USD, собственник, скачивание разрешено).
- **`completeness`** в ответе показывает, чего не хватает для публикации:
  `{"is_complete": false, "missing_fields": ["price", "area", "photos"]}`.
  У участков комнаты и этажи не спрашиваются.
- **Снижение цены у активного объявления** сохраняет прежнюю в `old_price` —
  из неё карточка рисует зачёркнутое «было 107 000$».
- **Лимит активных объявлений** проверяется и при публикации, и при возврате из
  архива; превышение — `409` с понятным сообщением. Значение берётся из
  `get_listings_limit(user)`: `FREE_ACTIVE_LISTINGS` (3) без подписки и
  `tariff.listings_limit` с ней (см. «Подписки и тарифы»).
- **`is_trusted`** у пользователя публикует объявление сразу в `active`
  с `expires_at = now + 30 дней`, остальные уходят в `pending`.
- **Мягкое удаление**: `is_deleted` + менеджеры `Listing.objects` (без удалённых)
  и `Listing.all_objects` (все). `base_manager_name = "all_objects"`, чтобы
  связанные объекты — история просмотров, избранное, операции кошелька —
  не ломались.
- **Права**: чужое опубликованное объявление — `403` (владение не секрет),
  чужой черновик — `404` (его существование не раскрываем).
- **`bump`** бесплатно раз в сутки, иначе `429` с `retry_after`.
- **`catalog.expire_listings`** (Beat, ежедневно) архивирует истёкшие объявления
  и за три дня предупреждает владельца.

## Медиафайлы объявления

| Метод | Путь | Что делает |
|---|---|---|
| POST | `/api/v1/listings/{slug}/media/` | загрузка пачки файлов (multipart, поле `files`) |
| PATCH | `/api/v1/listings/{slug}/media/reorder/` | новый порядок: `{"order": [12, 8, 3, 5]}` |
| POST | `/api/v1/listings/{slug}/media/{id}/set-cover/` | сделать файл обложкой |
| DELETE | `/api/v1/listings/{slug}/media/{id}/` | удалить запись и все варианты файлов |

**Загрузка пачкой.** Пользователь выбирает файлы в галерее скопом, поэтому
эндпоинт принимает список. Если файлов больше, чем свободных слотов, берётся
столько, сколько влезает, — как `AppState._append` во Flutter:

```json
{"accepted": 2, "rejected": 3, "reason": "Достигнут лимит 20 фото",
 "free_slots": 0, "media": [{"id": 41, "status": "processing", "url": "…"}]}
```

Слотов не осталось совсем — `400 validation_error` с
`details: {"free_slots": 0, "message": "Достигнут лимит 20 фото"}`
(во Flutter это `freePhotoSlots`).

**Проверки.** Тип определяется по содержимому (`apps/common/files.py`:
python-magic → сигнатуры → Pillow), а не по расширению и не по `Content-Type`:
`.jpg` с PDF внутри отклоняется. Фото — JPEG/PNG/HEIC, ≤ 15 МБ, ≥ 600×400.
Видео — MP4/MOV, ≤ 200 МБ, ≤ 180 секунд; длительность читается `ffprobe`
**до** сохранения, чтобы файл на четыре минуты не попал в бакет.

**Обработка** — Celery-задача `catalog.process_media(media_id)`:

1. **EXIF снимается первым и полностью.** В метаданных снимка квартиры лежат
   GPS-координаты, модель телефона и время съёмки; ни один вариант
   изображения не собирается из данных, где они ещё есть.
2. Три размера: `thumb` 400px, `medium` 1080px, `original` ≤ 2560px.
3. WebP (quality 82) + JPEG-фолбэк для старых клиентов.
4. Видео: кадр-превью на первой секунде (`ffmpeg`), длительность и разрешение
   (`ffprobe`). Само видео не перекодируется — дорого.
5. `imagehash.phash` фотографии пишется в `ListingMedia.phash`: одинаковый хеш
   в разных объявлениях означает переклеенный чужой снимок, и модератор видит
   это в админке (поиск по `phash`).
6. По завершении `status = ready`, заполнены `width`, `height`,
   `duration_seconds`, `size_bytes` и все варианты URL.

Пока `status != "ready"`, в поле `url` отдаётся оригинал — экран не ждёт
конвертации, только что снятая фотография видна сразу.

**Ключи в хранилище** — `listings/{listing_uuid}/{media_uuid}_{variant}.webp`.
Имя файла с телефона отбрасывается целиком: «паспорт_Иванов.jpg» — это ПДн,
а ключ попадает в публичный URL. Ни `slug`, ни последовательный `pk` в путь
не идут.

**Обложка и порядок.** Обложка всегда ровно одна (частичный уникальный
индекс). Удаление обложки передаёт её первой оставшейся фотографии.
Перестановка идёт в два прохода внутри транзакции: ограничение
`(listing, order)` проверяется построчно, поэтому номера сначала уводятся за
пределы занятого диапазона, а потом проставляются нужные.

Для видео нужен `ffmpeg` — он ставится в образ; без него загрузка не падает,
но длительность и превью не заполняются.

## Модерация объявлений

| Метод | Путь | Что делает |
|---|---|---|
| GET | `/api/v1/moderation/queue/` | очередь: `?status=open&has_triggers=true` |
| GET | `/api/v1/moderation/reject-reasons/` | справочник причин для формы отклонения |
| POST | `/api/v1/moderation/{task_id}/assign/` | взять задачу себе |
| POST | `/api/v1/moderation/{task_id}/approve/` | опубликовать на 30 дней |
| POST | `/api/v1/moderation/{task_id}/reject/` | `{"reason_code": "contacts", "comment": "…"}` |
| POST | `/api/v1/listings/{slug}/report/` | жалоба пользователя (`IsAuthenticated`) |

Все эндпоинты модерации требуют `is_staff`; обычный пользователь получает `403`
и не видит ни задач, ни результатов автопроверок.

**Очередь** отсортирована по `-priority`, затем по `created_at`. Каждая запись —
объявление целиком, `checks` с деталями и `author_rejections`: прошлые
отклонения этого автора. Третье объявление с контактами в описании от одного
человека — уже не случайность, и это видно до открытия карточки. История
подгружается пачкой на всю страницу, поэтому число запросов не растёт с
`page_size` (проверено тестом).

**Автопроверки** (`apps/catalog/moderation/checks.py`) запускаются задачей
`catalog.run_moderation_checks(listing_id)` при переводе объявления в `pending`.
Каждая возвращает `{"triggered": bool, "details": {...}}`, результат ложится
в `ModerationTask.checks`, `priority` = число сработавших:

1. **`contacts_in_text`** — телефоны (в том числе «0 555 12 34 56» и
   продиктованные словами), ссылки, WhatsApp/Telegram/Instagram в описании и
   адресе. Контакты в тексте — способ увести сделку мимо площадки, поэтому
   проверка намеренно параноидальная. Площадь, этажность и год постройки при
   этом не срабатывают: телефоном считается только 9–13 цифр подряд, а
   числительными — четыре и больше подряд.
2. **`price_outlier`** — цена за м² против медианы по району и типу за 90 дней,
   порог 3 сигмы. Меньше 10 объектов в районе — проверка **пропускается**:
   медиана по пяти объектам ничего не значит, а ложная метка стоит времени.
   Если все соседи стоят одинаково (сигма нулевая), используется относительный
   порог `MODERATION_PRICE_FALLBACK_RATIO`.
3. **`duplicate_listing`** — активное объявление **другого** пользователя с той
   же связкой (район, площадь ±2 м², этаж, комнаты, цена ±3 %).
4. **`duplicate_photos`** — `ListingMedia.phash` с расстоянием Хэмминга ≤ 5 в
   объявлениях других пользователей. Перцептивный хеш переживает пережатие, так
   что переклеенный чужой снимок находится даже пересохранённым.

Упавшая проверка не роняет остальные — в её результат пишется класс ошибки.

**Отклонение** берёт причину из справочника `RejectReason` (заводится
миграцией `0016_reject_reasons`, редактируется в админке). В
`listing.rejection_reason` кладётся готовый текст: владелец видит его без
обращения к справочнику, а правка формулировки задним числом не переписывает
уже отправленное решение.

**Повторная подача.** PATCH объявления в статусе `rejected` разрешён;
`publish/` заводит **новую** `ModerationTask`, прошлая остаётся историей.
Открытая задача при этом всегда одна — на это есть частичный уникальный индекс.

**Жалобы.** `ListingReport` — одна на пользователя на объявление (уникальное
ограничение: иначе порог накручивается одним человеком). Три неразрешённые
жалобы автоматически переводят активное объявление в `pending` и заводят задачу
с `priority=10` и пометкой `user_reports` в `checks` — ждать очереди, пока люди
видят мошенническое объявление, нельзя. Одобрение возвращает объявление и
закрывает жалобы.

**Админка**: `ModerationTask` с превью обложки, текстом объявления, таблицей
автопроверок и действиями approve/reject прямо из списка; фильтры по статусу,
приоритету и причине отклонения.

## Публичные эндпоинты каталога

| Метод | Путь | Что делает |
|---|---|---|
| GET | `/api/v1/listings/` | лента активных объявлений, курсорная пагинация, `?ordering=` |
| GET | `/api/v1/listings/{slug}/` | полная карточка объекта с медиа и продавцом |
| POST | `/api/v1/listings/{slug}/view/` | отметка просмотра → `{"views_count": 1043}` |
| GET | `/api/v1/listings/featured/` | подборки главного экрана по типам, кэш 5 минут |
| GET | `/api/v1/listings/{slug}/similar/` | шесть похожих объектов |

Всё `AllowAny`; от аутентификации зависят только `is_favourite` и телефон продавца.

- **Продвинутые вперёд.** Объявления с `promoted_until` в будущем всегда выше
  остальных при любой сортировке (`("-promoted_rank", <ordering>, "-id")`).
  `?ordering=` принимает `-published_at` (по умолчанию), `price`, `-price`,
  `-views_count`, `area`; всё остальное игнорируется.
- **Телефон продавца**: полный только авторизованным, анониму — маска
  `+996 7XX XXX XX6` (код страны, первая цифра оператора, последняя цифра).
- **Отметка просмотра** дедуплицируется ключом Redis `view:{slug}:{user|ip}` с TTL
  30 минут (`cache.add` — атомарно). Счётчик растёт через `F()`, история просмотров
  обновляется через `update_or_create`.
- **Запросы**: список — **3 SQL** для анонима и 4 для авторизованного, независимо от
  размера страницы (COUNT + выборка + prefetch обложек; `is_favourite` — подзапрос
  `Exists`, обложки — `Prefetch(to_attr=...)`, всё остальное — `select_related`).
  Карточка и «похожие» — по 3 запроса.

> Оговорка про курсор: DRF строит позицию курсора по **первому** полю сортировки,
> а у нас это флаг продвижения с двумя значениями. Внутри блока непродвинутых
> объявлений курсор вырождается в offset, который упирается в `offset_cutoff = 1000`
> (≈50 страниц по 20). Для мобильной ленты этого достаточно; если понадобится
> листать глубже — продвинутые объявления нужно отдавать отдельным блоком на первой
> странице, а не смешивать с общей сортировкой.

## Кошелёк и «кирпичи»

| Метод | Путь | Что отдаёт |
|---|---|---|
| GET | `/api/v1/wallet/` | `{"balance": 16700, "balance_display": "16.700", "currency": "brick"}` |
| GET | `/api/v1/wallet/transactions/?kind=topup\|spend\|bonus` | историю, сгруппированную по дням |

- **`apply_transaction()` — единственный способ изменить баланс**
  ([services.py](apps/billing/services.py)). Внутри: `transaction.atomic`,
  `select_for_update` на строке кошелька, проверка овердрафта, запись в леджер
  с `balance_after`. Прямых присваиваний `wallet.balance` в остальном коде нет —
  проверяется грепом по репозиторию.
- **Леджер append-only**: `save()` при наличии `pk` и `delete()` поднимают
  `RuntimeError`. Ошибочная операция компенсируется обратной, а не правкой —
  история должна оставаться тем, что действительно произошло.
- **Идемпотентность** по `idempotency_key`: повторный вызов возвращает уже
  созданную операцию, не трогая баланс. На этом же ключе строится повторная
  обработка платёжного вебхука.
- **Минус невозможен на трёх уровнях**: проверка в сервисе, блокировка строки
  и `CheckConstraint(balance >= 0)` в самой БД как последний рубеж.
- **Нехватка средств** — `402` с `details`: `{"required": 780, "available": 300}`,
  чтобы приложение сразу предложило пополнение на недостающую сумму.
- **Формат баланса** как в макете: `16700 → "16.700"`, `1200000 → "1.200.000"`.
- Кошелёк создаётся сигналом при регистрации пользователя.

  `PAYMENT_IDEMPOTENCY_TTL_HOURS` возвращает тот же ответ), проверка статуса
  в обработчике вебхука и ключи `payment-{id}-main` / `payment-{id}-bonus`
  у операций леджера. Повторный вебхук физически не может начислить дважды.
- **Кирпичи начисляются только через `apply_transaction`** — двумя операциями:
  основная и бонусная (`TOPUP_BONUS_RATE`, по умолчанию 10%).
- **Просроченный счёт не начисляется**: `billing.expire_payments` (Beat, каждые
  5 минут) переводит неоплаченные счета в `expired`, а вебхук по такому счёту
  отвечает 200 с пометкой в журнале — провайдер не должен ретраить.
- **Сумма из вебхука сверяется со счётом**: расхождение — повод не начислять,
  а записать инцидент в лог.
- **`PaymentLog` хранит обмен без платёжных данных**: ключи с `card`, `pan`,
  `cvv`, `token`, `signature`, `secret`, `password` маскируются рекурсивно
  до записи, включая вложенные объекты и списки.
- **Провайдер подменяем**: `PaymentProvider` с `PaymentIntent`/`WebhookResult`,
  реализации `mock` (рисует настоящий QR через `qrcode`) и `bank` — заготовка
  с HMAC-SHA256 и TODO в местах, где нужны поля конкретного банка. Выбор —
  через `PAYMENT_PROVIDER`.

## Продвижение объявлений

| Метод | Путь | Что делает |
|---|---|---|
| GET | `/api/v1/promotions/pricing/` | предрасчёт: `?days=3&options=exact_targeting,whatsapp_base` |
| POST | `/api/v1/listings/{slug}/promote/` | покупка (нужен `Idempotency-Key`) |
| GET | `/api/v1/listings/{slug}/promotions/` | история продвижений объявления |
| GET | `/api/v1/listings/{slug}/stats/` | показатели по дням за 30 суток |
| POST | `/api/v1/listings/{slug}/phone/` | «показать телефон» (считается в статистику) |

**Расчёт и покупка разделены.** `pricing/` считает цену сколько угодно раз, не
делая ни одной записи, и отдаёт в том же ответе справочники пакетов и опций —
экран `ad_promo_page` рисует их отсюда, ничего не хардкодя:

```json
{"days": 3, "base_cost": 2340,
 "options": [{"code": "exact_targeting", "name": "…", "cost": 900}],
 "options_cost": 1650, "total_cost": 3990,
 "balance": 20000, "is_affordable": true,
 "promoted_until_after": "2026-08-25T10:00:00+06:00"}
```

Пакеты и опции — справочники (`PromotionPackage`, `PromotionOption`), заведённые
миграцией `0008_promotion_catalog`: базовый пакет 780 кирпичей/день, как
`AppState.promoCost`. Цену меняют в админке, без релиза.

**Покупка** — один `transaction.atomic()`: объявление должно быть `active`
(иначе `409`), затем создаётся `Promotion`, затем `apply_transaction` списывает
кирпичи. При нехватке средств `InsufficientFundsError` поднимается **внутри**
блока, поэтому откатывается всё — ни продвижения, ни операции, ни изменения
баланса. В `details` уходит `{"required": …, "available": …, "shortfall": …}`;
приложение по коду `insufficient_funds` открывает экран пополнения на
недостающую сумму.

**Продление складывается с остатком**: три дня поверх двух неистёкших дают
пять, а не три (`max(now, promoted_until) + days`).

`Idempotency-Key` обязателен. Повторный запрос с тем же ключом возвращает уже
купленное продвижение и не списывает второй раз — ключ ищется по операции
леджера, а не по отдельной таблице.

### Статистика объявления

`ListingDailyStat` (listing, date, impressions, views, favourites,
phone_reveals) с уникальной парой (listing, date). Счётчики инкрементируются
F-выражениями из соответствующих эндпоинтов:

- **показы** — батчем. Страница каталога из двадцати карточек даёт двадцать
  событий на один запрос, поэтому id копятся в Redis (`HINCRBY` по одному хешу
  на сутки — атомарно и забирается одним `HGETALL`), а в БД их переносит
  `catalog.flush_impressions` раз в пять минут. Без Redis (тесты, dev) буфер
  вырождается в один ключ кэша;
- **просмотры** — из `POST /listings/{slug}/view/`, с той же 30-минутной
  дедупликацией, что и `views_count`;
- **избранное** — из `add_favourite`, только при реальном добавлении;
- **показы телефона** — из `POST /listings/{slug}/phone/`. Собственные
  нажатия владельца не считаются.

Ряд отдаётся за 30 дней **без пропусков**: дни без событий приходят нулями,
иначе график с дырами читается как «данных нет». Если объявление продвигалось,
добавляется `promotion_effect` — средние за сутки до продвижения и во время
него: абсолютные числа за месяц владельцу ничего не говорят, а разница средних
говорит.

### Фоновые задачи

`billing.expire_promotions` (ежечасно, :05) закрывает истёкшие продвижения и
снимает `promoted_until` — но только когда у объявления не осталось ни одного
действующего продвижения: их может быть несколько. За 24 часа до окончания
уходит уведомление `promotion_expiring`; поле `expiry_notified_at` гарантирует,
что оно отправится один раз, а не каждый час.

## Подписки и тарифы

| Метод | Путь | Что делает |
|---|---|---|
| GET | `/api/v1/tariffs/` | активные тарифы (`AllowAny`), у текущего `is_current` |
| POST | `/api/v1/subscriptions/` | покупка или продление (нужен `Idempotency-Key`) |
| GET | `/api/v1/subscriptions/current/` | тариф, срок и остаток свободных слотов |
| POST | `/api/v1/subscriptions/cancel/` | отключить автопродление |

Тарифы — справочник `Tariff`, заведённый миграцией `0010_tariffs`:
`free` (0 кирпичей, 3 объявления), `realtor` (4900/мес, 20 объявлений),
`agency` (14900/мес, без ограничений). `listings_limit = 0` означает «без
ограничений». Фичи лежат в `features` одним JSON с полным набором ключей, чтобы
у всех тарифов набор совпадал: `priority_in_search`, `advanced_stats`,
`verified_badge`, `auto_bump_daily`, `support_priority`.

**Три сценария покупки**, и они действительно разные:

- **продление того же тарифа** — сроки складываются, остаток не сгорает;
- **переход на более дорогой** — действует сразу, остаток прежнего периода
  засчитывается по дням (pro rata): за эти дни уже заплатили;
- **переход на более дешёвый** — стартует только после окончания оплаченного
  периода, иначе пользователь терял бы разницу, за которую заплатил.

Месяц подписки — фиксированные 30 суток (`MONTH_DAYS`): календарные месяцы
разной длины сделали бы pro rata непредсказуемой.

**Отмена** снимает только `is_auto_renew`. Подписка продолжает действовать до
конца оплаченного периода, а статус `cancelled` проставит суточная задача по
истечении — оплаченное не отбирается.

### Лимит объявлений

`get_listings_limit(user)` — единственный источник правды: без подписки
`settings.FREE_ACTIVE_LISTINGS`, с подпиской `tariff.listings_limit`. Публикация
(`ensure_free_slot`) и экран подписки спрашивают лимит здесь, а не считают сами.
Каталог импортирует биллинг локально внутри функции — модульной зависимости
каталога от биллинга нет.

### Приоритет в выдаче

Порядок ленты: **продвинутые → подписчики с `priority_in_search` → все
остальные**. Купленное продвижение всегда выше тарифного приоритета: за него
заплатили отдельно и за конкретное объявление. Реализовано аннотацией
`priority_rank` — один подзапрос `EXISTS` по активным подпискам на весь список,
без запроса на карточку (проверено тестом на неизменность числа запросов при
росте `page_size`).

### Фоновые задачи

`billing.process_subscriptions` (ежедневно, 06:00):

1. **автопродление** за 24 часа до `ends_at` при `is_auto_renew=True`. Ключ
   идемпотентности детерминированный (`subscription-renew-{pk}-{дата}`), так что
   повторный запуск задачи не спишет дважды. Нехватка средств — не ошибка, а
   обычный сценарий: уходит уведомление «Не удалось продлить подписку», баланс
   остаётся нетронутым, в минус не уходим никогда;
2. **истечение**: `ends_at < now` → `expired`, после чего активные объявления
   сверх нового лимита уходят **в архив** (не удаляются!), начиная с самых
   старых по `published_at` — свежие объявления актуальнее. Владельцу уходит
   уведомление с числом заархивированных.

Порядок шагов не случаен: сначала продление, потом истечение — иначе успешно
продлённая подписка тут же попала бы в «истёкшие».

`billing.auto_bump_listings` (ежедневно, 06:30, после обработки подписок)
поднимает объявления подписчиков с фичей `auto_bump_daily`, обновляя
`published_at`. Поле `auto_bumped_at` не даёт поднять дважды за сутки.

## Уведомления и push

| Метод | Путь | Что делает |
|---|---|---|
| GET | `/api/v1/notifications/?is_read=false&type=price_drop` | лента, курсорная пагинация |
| GET | `/api/v1/notifications/unread-count/` | `{"count": 7}` для бейджа |
| POST | `/api/v1/notifications/read/` | `{"ids": [...]}` или `{"all": true}` → новый `unread_count` |
| DELETE | `/api/v1/notifications/{id}/` | удалить своё уведомление |
| GET/PATCH | `/api/v1/notifications/settings/` | флаги push: общий и на каждый тип |
| POST | `/api/v1/devices/` | upsert устройства по токену |
| DELETE | `/api/v1/devices/{token}/` | деактивировать при выходе из аккаунта |

- **Единственная точка создания — `notify()`** ([services.py](apps/notifications/services.py)):
  создаёт `Notification` и ставит задачу push после коммита. Для рассылок есть
  `notify_many()` — тот же контракт, но одним `INSERT` (почасовая рассылка по
  сохранённым фильтрам не должна делать по запросу на пользователя). Модерация,
  кошелёк и фильтры вызывают только их.
- **Push — всегда через Celery** (`notifications.send_push`), синхронно из вьюх не шлём.
- **Настройки уважаются на отправке**: `push_enabled` и флаг конкретного типа. При
  выключенном push уведомление всё равно создаётся — оно видно в ленте.
- **Мёртвые токены гасятся**: если FCM ответил `UNREGISTERED` или `INVALID_ARGUMENT`,
  устройство помечается `is_active=False`. Отправка идёт multicast-батчами по 500,
  порядок токенов фиксирован — по нему ответы сопоставляются с устройствами.
- **Токен принадлежит устройству, а не аккаунту**: если на телефоне сменился
  пользователь, `POST /devices/` переносит токен на текущего — иначе push уходил бы
  прежнему владельцу.
- **Креды FCM** — из `FCM_CREDENTIALS_FILE` или `FCM_CREDENTIALS_BASE64`. Не заданы —
  push молча отключён, всё остальное работает.
- **`notifications.notify_price_drop`** (Beat, 10:00 Asia/Bishkek) сравнивает
  `Listing.price_usd` с `Favourite.price_at_add`; при падении ≥ 3% шлёт уведомление
  «Цена снизилась на 5%: Технопарк, 3-комн. — 97 000$» и обновляет отметку цены,
  чтобы о том же снижении не написать дважды.

## Избранное и история просмотров

| Метод | Путь | Что делает |
|---|---|---|
| POST/DELETE | `/api/v1/listings/{slug}/favourite/` | переключатель избранного, оба вызова идемпотентны |
| GET | `/api/v1/favourites/` | избранное в порядке добавления |
| GET | `/api/v1/view-history/` | история, сгруппированная по дням |
| DELETE | `/api/v1/view-history/` | удалить перечисленные записи или всю историю |

- **Идемпотентность.** Повторный `POST` не создаёт дубль и не двигает счётчик;
  `DELETE` несуществующей записи отвечает `200`, а `favourites_count` не уходит
  ниже нуля. Счётчик меняется `F()`-выражением в одной транзакции с записью.
- **Снятые с публикации объявления остаются** и в избранном, и в истории, но
  приходят с `is_available: false` — карточка показывается неактивной, а не исчезает.
- **Сортировка избранного** — по времени добавления записи, а не публикации объекта:
  курсор идёт по аннотации `favourited_at`.
- **История группируется по дням в Asia/Bishkek** (не по UTC-суткам сервера): `today`,
  `yesterday`, дальше `2026-08-18` / «18 августа». Группировка — один проход по
  отсортированной выборке, без запроса на каждый день. Пагинация тоже по дням:
  страница отдаёт целые дни, курсор указывает на последний из них.
- **Очистка**: `engagement.purge_view_history` в Beat раз в сутки удаляет записи
  старше `VIEW_HISTORY_RETENTION_DAYS` (90 дней).

Сервис `note_view(user, listing)` вызывается из `POST /listings/{slug}/view/`
(`update_or_create` по паре пользователь-объявление) и ничего не пишет для анонимов.

## Сохранённые фильтры и подборки

| Метод | Путь | Кто | Что делает |
|---|---|---|---|
| GET/POST | `/api/v1/saved-filters/` | авторизованный | список своих фильтров / сохранить новый |
| PATCH/DELETE | `/api/v1/saved-filters/{id}/` | владелец | переименовать, переключить уведомления, удалить |
| GET | `/api/v1/saved-filters/{id}/listings/` | владелец | каталог по сохранённым параметрам |
| GET | `/api/v1/collections/` | все | активные подборки по `order` |
| GET | `/api/v1/collections/{slug}/listings/` | все | объекты подборки |

- **Параметры проверяются тем же `ListingFilterSet`, что и каталог**: неизвестный ключ
  или негодное значение — `400 validation_error`, в базу попадает только нормализованный
  вид (значения строками, списки через запятую, пустые отброшены, ключи отсортированы).
  Одинаковые фильтры разных пользователей дают побайтово одинаковый `params` — на этом
  строится группировка в рассылке.
- **Лимит 20 фильтров** на пользователя, 21-й — `409 conflict`; повтор названия — тоже 409.
- **Чужие фильтры не видны**: для их владельца это `404`, а не `403`.
- **`PATCH` не меняет `params`** — иначе `last_notified_at` относился бы к прошлому
  запросу и пользователь пропустил бы новинки. Для другого набора создаётся другой фильтр.

### Рассылка по фильтрам

`engagement.notify_saved_filters` (Celery Beat, каждый час в :10) считает объявления,
опубликованные после `COALESCE(last_notified_at, created_at)`, и создаёт одно
уведомление `saved_filter_match` на фильтр. Фильтры обрабатываются пачками по 200
и группируются по одинаковым `params`: на группу приходится один `COUNT` и один запрос
за отметками публикации, дальше счёт идёт в памяти (`bisect`). После прогона
`last_notified_at` сдвигается на «сейчас», поэтому повторный запуск ничего не создаёт.

### Подборки

`Collection` работает в двух режимах: `query` — параметры каталога в `params`,
`manual` — список объектов через `CollectionItem` с полем `order`. В ручном режиме
порядок задаёт редактор, поэтому и пагинация идёт по `item_order`, а не по правилам
каталога (продвинутые вперёд + сортировка). Неактивные подборки и неактивные
объявления внутри них наружу не отдаются.

## Объявления

`Listing` и `ListingMedia` ([models.py](apps/catalog/models.py)) — центральные сущности каталога.

- **Слаг** генерируется один раз при создании: `<district-slug>-<rooms>k-<8 hex>`
  (`technopark-3k-9f1c2a4b`). Дальше он не меняется — по нему строятся ссылки,
  которыми делятся пользователи.
- **Город продублирован** рядом с районом (`Listing.city`): фильтр по городу — самый
  частый запрос каталога, и джойн ради него делать не хочется.
- **Лимиты медиа** — `MAX_PHOTOS_PER_LISTING` / `MAX_VIDEOS_PER_LISTING` = 20
  ([constants.py](apps/catalog/constants.py)), как `AppState.draftMediaLimit` во Flutter.
  Проверяются и в сервисе `add_listing_media()`, и в `ListingMedia.clean()` — запись
  мимо сервиса тоже не пройдёт.
- **Обложка** — ровно одна на объявление: `UniqueConstraint` с
  `condition=Q(is_cover=True)`. Первое фото становится обложкой автоматически.
- **Счётчики** `views_count` и `favourites_count` денормализованы и меняются
  **только** сервисными функциями через `F()`-выражения (`register_view`,
  `increment_favourites`, `decrement_favourites`). Никаких сигналов в горячем пути
  и никакого read-modify-write в Python: параллельные инкременты не должны теряться.
- **Свойства**: `is_plot`, `is_promoted`, `price_display` («102 000$», неразрывный
  пробел как в макете), `discount_percent`.
- **Индексы**: `(status, -published_at)`, `(status, district, kind)`, `(status, price)`,
  GIN по `search_vector` и GIN + `gin_trgm_ops` по `address` (расширение `pg_trgm`
  включается миграцией `0006`).

Перечисления вынесены в [enums.py](apps/catalog/enums.py): `PropertyKind`,
`SellerKind`, `ListingStatus`, `MediaKind`, `Currency`. **Значения совпадают с
enum'ами Flutter** — переименовывать нельзя, меняются только подписи.

> GIN-индексы и `pg_trgm` — фичи PostgreSQL. Целевая БД проекта — Postgres 16,
> но локальный прогон тестов идёт на SQLite, поэтому эти индексы создаются
> операцией `PostgresOnlyAddIndex` ([migrations_utils.py](apps/catalog/migrations_utils.py)):
> в состояние миграций они попадают всегда, в схему — только на Postgres.

## Справочники каталога и фильтр

| GET | `/api/v1/catalog/districts/?city=<slug>` | `[{id, name, slug, city, latitude, longitude}]` |

`filter-options` содержит `property_kinds`, `seller_kinds`, `rooms`, `area_ranges`,
`series`, `districts` и `price_range`. **Значения `property_kinds` и `seller_kinds`
совпадают с enum'ами Flutter** (`lib/data/listings.dart`) — переименовывать их нельзя.
`price_range` — агрегат `MIN/MAX` по активным объявлениям выбранного города
(при их отсутствии — `CATALOG_DEFAULT_PRICE_MIN/MAX`).

Ответ кэшируется на 10 минут; ключ учитывает город и `Accept-Language`.
Инвалидация — сигналами `post_save`/`post_delete` на `District`, `HouseSeries`,
`Listing` и `City` через счётчик версии в ключе: сбрасывать нужно все города сразу,
а перечислять их в сигнале — лишние запросы к БД. При попадании в кэш эндпоинт
**не делает ни одного SQL-запроса** (город резолвится только при промахе).
Сбой Redis не ломает сохранение объектов: ошибка инвалидации только логируется.

## Верификация личности исполнителя (KYC)

Экраны загрузки селфи и фото документа. Это самые чувствительные данные системы,
поэтому режим обращения с ними строже, чем с остальными файлами.

| Метод | Путь | Кто | Что делает |
|---|---|---|---|
| POST | `/api/v1/verification/identity/` | pro | подать селфи и фото документа (multipart) |
| GET | `/api/v1/verification/identity/` | любой авторизованный | статус своей последней заявки |
| GET | `/api/v1/verification/queue/` | staff + `users.can_review_identity` | очередь заявок с подписанными ссылками |
| POST | `/api/v1/verification/identity/{id}/review/` | staff + `users.can_review_identity` | `approve` / `reject` |

**Отдельное приватное хранилище.** Файлы KYC не лежат рядом с медиа объявлений:
локально это каталог `PRIVATE_MEDIA_ROOT` вне `MEDIA_ROOT`, в облаке — отдельный бакет
`AWS_PRIVATE_STORAGE_BUCKET_NAME` с block-public-access и без CDN-домена. Локальный
бэкенд (`apps/common/storages.py`) вообще не умеет отдавать URL — `storage.url()`
бросает исключение, так что «случайно» получить прямую ссылку нельзя.

**Подписанные ссылки.** Единственный доступ к файлу — ссылка со сроком жизни
`KYC_SIGNED_URL_TTL` (10 минут). На S3 это presigned URL, локально — токен
`django.core.signing`, привязанный к конкретному сотруднику: переслать ссылку коллеге
не выйдет. **Каждая выдача ссылки и каждое скачивание пишутся в `AuditLog`**: кто,
чьи документы, когда и с какого IP.

**Обработка при загрузке.** Тип файла определяется по содержимому (`python-magic`,
с откатом на Pillow, если libmagic нет в системе), проверяются размер (≤ 10 МБ)
и разрешение (≥ 800×600). Фоновая задача `users.process_identity_documents`
полностью пересобирает изображение без EXIF/GPS и удаляет исходник. Публичных
превью не создаётся, в CDN эти файлы не попадают.

**Право доступа.** `is_staff` сам по себе не даёт ничего: нужно отдельное разрешение
`users.can_review_identity` (выдаётся в админке). Без него — 403 и на очередь, и на review.

**Удаление.** После решения выставляется `purge_after = now + KYC_PURGE_AFTER_DAYS`
(30 дней). Celery Beat раз в сутки (03:45) запускает `users.purge_identity_files`:
файлы удаляются из хранилища, поля очищаются, **сама запись остаётся** — факт проверки
нужен, сканы паспорта нет.

**Логи.** Имена файлов, их содержимое и подписанные ссылки в обычные логи не пишутся;
в `AuditLog.extra` попадает только имя поля (`selfie`, `document_front`).

## Публичный профиль продавца и отзывы

| Метод | Путь | Что делает |
|---|---|---|
| GET | `/api/v1/sellers/{user_id}/` | карточка продавца (`AllowAny`) |
| GET | `/api/v1/sellers/{user_id}/listings/` | его активные объявления, фильтры каталога |
| GET/PATCH | `/api/v1/sellers/me/` | свой профиль (`is_pro`) |
| GET/POST | `/api/v1/sellers/me/verification/` | документы агентства (multipart) |
| GET/POST | `/api/v1/sellers/{user_id}/reviews/` | отзывы: чтение публичное, запись — авторизованным |
| PATCH/DELETE | `/api/v1/reviews/{review_id}/` | свой отзыв |
| POST | `/api/v1/listings/{slug}/contact/` | раскрытие телефона, 30/час |

**Контакты**. Телефон целиком, WhatsApp и Telegram отдаются только
авторизованному; анониму приходит маска вида `+996 7XX XXX XX1` — иначе
страница продавца превращается в готовую выгрузку номеров. Instagram публичен:
это витрина, а не канал связи.

**Профиль** редактируется весь, кроме `rating`, `reviews_count` и
`is_verified`: рейтинг — агрегат отзывов, значок проверенного ставит модератор.
`working_hours` валидируется по форме `{"mon": ["09:00", "18:00"], "sun": []}` —
пустой список означает выходной.

### Отзывы

Один отзыв на продавца от пользователя (уникальная пара `(seller, author)`),
повтор — `409`; чтобы изменить, есть PATCH своего отзыва. Отзыв самому себе —
`400`. Создаётся со статусом `pending` и уходит в общую очередь модерации;
правка опубликованного возвращает его в `pending`, чтобы модерация проверяла
ровно то, что читают.

**Рейтинг денормализован**, но пересчитывается только явным вызовом
`recalc_seller_rating(seller)` — из публикации, правки, отклонения и удаления
отзыва. Сигналом на `Review.save()` он пересчитывался бы и на черновиках, и на
отклонённых, и на любом служебном touch записи.

### Модерация отзывов

Очередь одна, чтобы модератор не переключался между двумя списками: у
`ModerationTask` теперь либо `listing`, либо `review` (CHECK-ограничение
требует хотя бы одного), а `?target=listing|review` фильтрует. У отзывов нет
автопроверок, поэтому их приоритет нулевой и они разбираются после
подозрительных объявлений. То же доступно в админке действиями
«Опубликовать»/«Отклонить».

### Раскрытие контактов и антифрод

`POST /listings/{slug}/contact/` отдаёт телефон, инкрементирует
`ListingDailyStat.phone_reveals` и пишет `ContactEvent` (объявление,
пользователь, IP, время). Порог `30/hour` на пользователя — не про удобство:
живой человек за час открывает единицы номеров, а скрипт-выгрузка — сотни.
Собственные нажатия владельца не считаются и события не создают.

### Подтверждение агентства

`SellerVerification` — это **не** KYC: здесь документы юрлица, а не паспорт,
поэтому они лежат в обычном хранилище, а не в приватном. Имя файла с телефона
в ключ не попадает (может содержать ПДн) — только расширение. Вторая заявка,
пока первая на проверке, — `409`. Одобрение ставит `is_verified` и
`verified_at`.

## Пользователь и профиль

`AUTH_USER_MODEL = "users.User"`, `USERNAME_FIELD = "phone"`, пароля в обычном
сценарии нет — вход по SMS-коду.

| Метод | Путь | Что делает |
|---|---|---|
| GET | `/api/v1/users/me/` | профиль: `id`, `phone`, `name`, `is_pro`, `iin`, `avatar_url`, `date_joined`, `wallet_balance` |
| PATCH | `/api/v1/users/me/` | меняет **только** `name` и `avatar`; `phone`, `is_pro`, `iin`, `is_staff` объявлены read-only и молча игнорируются |
| DELETE | `/api/v1/users/me/` | мягкое удаление, `204` |

- **Телефон** нормализуется к E.164 через `phonenumbers` (регион по умолчанию `KG`)
  в `User.save()`: «0700 12-34-56» → `+996700123456`. Невалидный номер — `ValidationError`,
  наружу это выходит как `400 validation_error`.
- **ИИН — персональные данные.** В API отдаётся маскированным (`20101199******`);
  полное значение видят только сам владелец и staff. В `__str__`, логи и текст ошибок
  ИИН не попадает; в админке поле read-only.
- **Мягкое удаление** (`apps/users/services.py`): `is_active=False`, телефон меняется на
  `deleted-<8 hex>`, имя/ИИН/аватар стираются, пароль становится неиспользуемым,
  все объявления пользователя уходят в `archived`. Строка в БД остаётся — на неё
  ссылаются объявления, обращения и операции по кошельку.
- `wallet_balance` — вложенный объект `{"balance": <кирпичи>, "currency": "brick"}`;
  берётся из кошелька, если он заведён, иначе `0`.

### Фикстуры

`tests/conftest.py`: `api_client`, `auth_client`, `pro_client`, `admin_client`,

Фабрики — на все 43 модели проекта (`tests/factories.py`).

### Тесты гонок

`tests/test_concurrency.py` поднимает настоящие параллельные соединения
(потоки + `django_db(transaction=True)`), а не мокает блокировки: смысл
проверки именно в том, что `SELECT ... FOR UPDATE` и уникальные ограничения
работают на реальном движке.

Поэтому три таких теста идут **только на PostgreSQL**. SQLite сериализует
запись на уровне файла и игнорирует `select_for_update` — «зелёный» результат
там ничего не доказывал бы. Рядом лежат детерминированные проверки тех же
инвариантов: они идут везде и ловят регрессию в логике, хоть и не гонку.

```bash
DATABASE_URL=postgres://house:house@localhost:5432/house make test-concurrency
```

### Контракт OpenAPI

`tests/snapshots/openapi.json` — обещание, данное мобильному приложению.
Ломающими считаются три вещи: пропал эндпоинт (старая сборка получит 404),
пропало поле ответа (клиент упадёт на разборе), ужесточился тип — сменился,
перестал быть nullable или потерял вариант enum. Добавлять эндпоинты, поля и
значения enum можно свободно.

Отдельно проверяется, что схема генерируется **без предупреждений**
drf-spectacular: его warning — это дыра в схеме, по которой кодогенератор
соберёт неправильный клиент.

Обновление снапшота — осознанное действие: `make schema-update`.

## Безопасность и персональные данные

Проект хранит телефоны и ИИН граждан Кыргызстана. Ниже — не рекомендации, а
действующие ограничения.

### Ограничение частоты (`apps/common/throttling.py`)

| Эндпоинт | Лимит | Ключ |
|---|---|---|
| `/auth/otp/request/` | 1/мин и 5/час | номер (нормализованный) |
| `/auth/otp/request/` | 20/час | IP |
| `/auth/password/login/` | 10/час, 30/час | номер, IP |
| `/listings/{slug}/contact/` | 30/час | пользователь |
| загрузка медиа | 100 **файлов**/час | пользователь |
| `/wallet/topup/` | 10/час | пользователь |
| всё остальное | 100/мин аноним, 300/мин пользователь | IP / пользователь |

Счётчики в Redis — лимит общий для всех воркеров: с четырьмя процессами
gunicorn «5 в час» должно оставаться пятью, а не двадцатью. Номер
нормализуется до ключа: «0555 12 34 56» и «+996555123456» — один счётчик.

Лимит медиа считает **файлы, а не запросы**, и пропускает пачку целиком или
не пропускает вовсе: «хватило места первому файлу» не значит «хватило всем».

Превышение — `429` с `details.retry_after`.

### Логи без персональных данных

Маскирование работает **процессором structlog и фильтром logging**, а не
дисциплиной разработчиков. Любой `logger.info(...)`, любое исключение с
номером в тексте, любая сторонняя библиотека проходят через один фильтр до
записи в stdout. Полагаться на то, что никто никогда не залогирует телефон,
— значит однажды его залогировать.

```
+996700123456       -> +996 7XX XXX XX6
20101199001234      -> 20**********34
user@example.kg     -> u***@example.kg
eyJhbGciOi…         -> ***
```

Маска сохраняет узнаваемость — по логам всё ещё можно разбирать инциденты.
Площадь, этаж, год постройки и цена не маскируются: 6 цифр — не телефон.
Ключи `request_id`, `payment_id`, `slug` в списке исключений, иначе маска
токенов съедала бы идентификаторы, по которым логи связываются в цепочку.

Каждая запись содержит `request_id`, `user_id`, `path`, `method`, `status`,
`duration_ms`. `request_id` приходит из `X-Request-ID` (значение снаружи
чистится — иначе это инъекция в лог) или генерируется, и возвращается
клиенту в заголовке ответа.

Формат: JSON в production, читаемая строка локально (`LOG_JSON`).

### Журнал аудита

`audit(actor, action, target, changes, request)` — **явный вызов**, не сигнал:
сигнал видит факт изменения, но не знает, кто его инициировал и с какого
адреса, а запись без актора и IP не отвечает на вопрос, ради которого журнал
и заводят.

Пишется при: операции по кошельку, зачислении платежа, решении модерации
(объявления и отзывы), изменении цены объявления, входе по паролю (успешном и
нет), удалении аккаунта, выдаче согласия, выгрузке данных, решении по
верификации. Значения в `changes` и `extra` проходят то же маскирование, что
и логи: журнал читает персонал, а телефон — ПДн и там.

### Шифрование ИИН

`EncryptedCharField` (Fernet, ключ из `FIELD_ENCRYPTION_KEY`) — в БД лежит
`enc:gAAAAA…`, дамп базы не содержит ИИН открытым текстом (проверяется тестом
сырым SQL). Шифрование не детерминированное: два одинаковых ИИН дают разный
шифротекст, иначе он подбирается перебором.

Почему не pgcrypto: шифрование на стороне БД привязывает проект к PostgreSQL
(тесты идут на SQLite), а ключ пришлось бы передавать в каждом запросе — то
есть он оказался бы в логах медленных запросов.

Плата за это — по ИИН нельзя искать. Искать людей по ИИН и не нужно.

Существующие данные шифрует миграция `users/0009_encrypt_existing_iin`;
обратная миграция расшифровывает.

### Согласие на обработку ПДн

`UserConsent` хранит историю: тип согласия, **версию документа**, время и IP.
Закон требует уметь показать, какую именно редакцию человек принял.

`POST /auth/otp/verify/` без `accepted_terms_version` для нового пользователя
— `400`, аккаунт не создаётся. Согласие проверяется **до** создания записи:
созданный и тут же брошенный пользователь — уже обработка ПДн. Устаревшая
версия тоже отклоняется, в `details` приходит актуальная.

Повторный вход согласия не требует — оно спрашивается один раз на версию.

### Права субъекта данных

| Метод | Путь | Что делает |
|---|---|---|
| POST | `/api/v1/users/me/export/` | собрать все свои данные в JSON |
| GET | `/api/v1/users/me/export/{token}/` | скачать по подписанной ссылке (24 ч) |
| GET/POST | `/api/v1/users/me/consents/` | согласия |
| DELETE | `/api/v1/users/me/` | удалить аккаунт |

Выгрузка собирается Celery-задачей и кладётся в **приватное** хранилище:
это всё, что мы знаем о человеке, одним файлом. Не чаще одной в сутки.

Удаление аккаунта дополнительно ставит `users.purge_user_data`: физически
удаляются медиафайлы объявлений, логотип, прошлые выгрузки; операции
кошелька **остаются** (нужны бухгалтерии и сходимости баланса), но
обезличиваются — подпись становится «операция удалённого аккаунта», а
контактные телефоны из объявлений стираются.

### Заголовки и админка (production)

HSTS на год с `preload` и `includeSubDomains`, `SECURE_SSL_REDIRECT`,
`SESSION_COOKIE_SECURE`, `CSRF_COOKIE_SECURE`, `SECURE_CONTENT_TYPE_NOSNIFF`,
`X_FRAME_OPTIONS=DENY`, `Referrer-Policy: strict-origin-when-cross-origin`,
CSP (`django-csp`) для админки и Swagger. Сессии персонала живут 8 часов и не
переживают закрытие браузера.

Админка: путь из `ADMIN_URL_PATH` (не `/admin/` — его сканируют боты),
доступ только с `ALLOWED_ADMIN_IPS`, обязательный второй фактор
(`django-otp`). Чужому адресу отвечает **404, а не 403**: существование
админки по этому пути — не то, что стоит подтверждать сканеру.

`production.py` **отказывается стартовать** без `ALLOWED_ADMIN_IPS`,
собственного `ADMIN_URL_PATH` и `FIELD_ENCRYPTION_KEY`. Забытая переменная
должна ронять деплой, а не тихо оставлять дыру.

## Наблюдаемость

**Sentry** (`sentry-sdk` с интеграциями Django, Celery, Redis).
`send_default_pii=False` принципиально: с ним Sentry сам приложит тело
запроса, заголовки и учётные данные — то есть телефоны и ИИН уедут стороннему
сервису. События дополнительно проходят через `before_send` с тем же
маскированием, что и логи.

**Prometheus** — `/metrics`, доступен только из `INTERNAL_NETWORKS`
(`InternalOnlyMiddleware`). Проверка в приложении дублирует ограничение nginx
осознанно: если приложение однажды окажется доступно напрямую, метрики не
утекут вместе с ним. Адрес берётся с учётом `X-Forwarded-For`.

Прикладные метрики (`apps/common/metrics.py`) — по ним видно, что система
работает неправильно, даже когда все ответы 200:

| Метрика | Тип |
|---|---|
| `house_listings_published_total{moderated}` | counter |
| `house_topup_bricks_total` | counter |
| `house_payments_failed_total{provider,reason}` | counter |
| `house_wallet_spend_bricks_total{purpose}` | counter |
| `house_media_processing_seconds{kind}` | histogram |
| `house_moderation_queue_size{target}` | gauge |

Gauge очереди обновляет задача `common.refresh_metrics` раз в две минуты:
считать его в момент скрейпа значило бы сделать `/metrics` источником
нагрузки на БД. Сбой записи метрики никогда не роняет бизнес-операцию.

## Проверка зависимостей

```bash
make audit       # pip-audit по установленным пакетам
make security    # ruff (включая S/bandit) + pip-audit
```

`ruff` включает набор `S` (bandit). Разбор находок: `assert` в тестах,
`random` в сидере и нагрузочных данных, «пароли» в именах настроек — это
шум, он вынесен в `per-file-ignores` с объяснением. Одна находка была
настоящей: `xml.etree` разбирал внешний XML НБКР и был уязвим к XML-бомбе —
заменён на `defusedxml`.

CI (`.github/workflows/backend.yml`) гоняет линт, `pip-audit`, тесты на
PostgreSQL и Redis (там тесты гонок **не пропускаются**), оба порога
покрытия и контракт OpenAPI.

## Конфигурация и секреты

Все настройки читаются из переменных окружения через `django-environ`.
В репозитории лежит только `.env.example`; `.env` в `.gitignore` и в git не попадает.
Обязательные переменные: `DJANGO_SECRET_KEY`, `DATABASE_URL`, `REDIS_URL`.
Полный список с комментариями — в [.env.example](.env.example).

Модуль настроек выбирается через `DJANGO_SETTINGS_MODULE`
(`config.settings.local` по умолчанию, `config.settings.production` в проде).

### Продакшн

`config/settings/production.py` включает `SECURE_SSL_REDIRECT`, `SECURE_HSTS_SECONDS`
(год, с subdomains и preload), `SESSION_COOKIE_SECURE`, `CSRF_COOKIE_SECURE`,
`X_FRAME_OPTIONS=DENY`; CORS-origin'ы берутся из `CORS_ALLOWED_ORIGINS`.
Образ по умолчанию запускается через gunicorn под non-root пользователем `app`;
статику собирает `COLLECT_STATIC=true`, миграции — `RUN_MIGRATIONS=true`.

Проверить перед деплоем:

```bash
DJANGO_SETTINGS_MODULE=config.settings.production python manage.py check --deploy
```
