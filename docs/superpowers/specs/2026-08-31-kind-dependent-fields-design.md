# Поля объявления, зависящие от типа недвижимости

Дата: 2026-08-31

## Проблема

Все шесть типов недвижимости используют один и тот же набор полей. У участка
нет комнат и этажей, но форма подачи требует их, карточка показывает «0 этаж из
12», а фильтр предлагает «103 серия» для земли. Для коммерции важны свои
параметры, которых в системе нет вовсе.

Единственная зависимость от типа во всём коде — `if not listing.is_plot` в
`missing_fields_for_publish` (`backend/apps/catalog/services.py:748`).

## Решение

Одна таблица «тип → применимые поля», продублированная на бэкенде и во
Flutter-клиенте (вариант A из обсуждения). Гибкости динамической схемы с сервера
здесь не нужно: шесть типов зафиксированы в ТЗ («значения enum'ов менять
нельзя»), а ручная вёрстка сохраняет нынешний стиль интерфейса. Переход на
серверную схему позже дёшев, потому что таблица вынесена в отдельный модуль.

## Матрица полей

Общие для всех типов: район, адрес, цена и валюта, площадь, описание, фото,
тип продавца, ипотека, прямая покупка.

| Поле | Квартира | Комната | Дом | Новостройка | Участок | Коммерция |
|---|:--:|:--:|:--:|:--:|:--:|:--:|
| `rooms` | ✓ | — | ✓ | ✓ | — | — |
| `floor` | ✓ | ✓ | — | ✓ | — | ✓ |
| `floors` | ✓ | ✓ | ✓ | ✓ | — | ✓ |
| `series` | ✓ | ✓ | — | — | — | — |
| `is_secondary` | ✓ | ✓ | ✓ | — | — | — |
| `builder` | — | — | — | ✓ | — | — |

Решения, принятые явно: у «Комнаты» поля `rooms` нет; новостройке серия дома не
нужна; высота потолков у коммерции есть, но никогда не обязательна.

## Бэкенд

### Новые поля модели `Listing`

Все добавляемые поля допускают пустое значение — миграция не должна ломать
существующие записи.

| Поле | Тип | Значения |
|---|---|---|
| `plot_purpose` | `CharField(choices, blank=True)` | `ihs`, `garden`, `agricultural`, `commercial` |
| `commercial_purpose` | `CharField(choices, blank=True)` | `office`, `shop`, `warehouse`, `production`, `catering`, `free` |
| `has_separate_entrance` | `BooleanField(default=False)` | — |
| `building_line` | `CharField(choices, blank=True)` | `first`, `second`, `inside` |
| `ceiling_height` | `DecimalField(4, 2, null=True, blank=True)` | метры |

Перечисления (`PlotPurpose`, `CommercialPurpose`, `BuildingLine`) объявляются в
`apps/catalog/enums.py` рядом с `PropertyKind`.

### Таблица правил

Новый модуль `apps/catalog/field_rules.py`:

- `KIND_FIELDS: dict[str, frozenset[str]]` — какие поля применимы к типу;
- `REQUIRED_BY_KIND: dict[str, tuple[str, ...]]` — какие обязательны для
  публикации;
- `applicable_fields(kind) -> frozenset[str]`;
- `strip_inapplicable(kind, data) -> dict` — убирает из входных данных ключи,
  неприменимые к типу.

Модуль не импортирует ничего из `services.py`, чтобы им могли пользоваться и
сериализаторы, и фильтры без циклических импортов.

### Точки применения

1. **`ListingUpdateSerializer.validate()`** вызывает `strip_inapplicable`.
   Неприменимое значение отбрасывается **молча**, без ошибки валидации: клиент
   шлёт PATCH всей формой по мере заполнения, и 400 на остаточном `rooms` от
   предыдущего выбора типа сломал бы обычный сценарий.
2. **`missing_fields_for_publish()`** читает `REQUIRED_BY_KIND[listing.kind]`
   вместо частного случая `if not listing.is_plot`. Требование «хотя бы одно
   фото» сохраняется для всех типов.
3. **`ListingFilterSet`** получает фильтры `plot_purpose`, `commercial_purpose`,
   `building_line`, `has_separate_entrance`. Существующие `rooms` и `series` не
   меняются — клиент просто не присылает их для неподходящих типов.

### Контракт API

- `ListingDetailSerializer`, `ListingDraftSerializer` и
  `ListingUpdateSerializer` получают пять новых полей.
- `/api/v1/catalog/filter-options/` дополняется словарями `plot_purposes`,
  `commercial_purposes`, `building_lines` — фронту нужны подписи, и это то же
  место, откуда он уже берёт районы и серии домов.
- Изменения аддитивные: добавление полей и вариантов enum совместимо по
  правилам `tests/test_openapi_contract.py`. Снапшот обновляется осознанно
  через `make schema-update`.

### Данные

Миграция только добавляет колонки. Существующие значения (например, `rooms` у
уже созданных участков) не чистятся: они перестанут показываться, а молча
затирать чужие данные без отдельного запроса нельзя.

## Фронтенд

### Общий источник правил

`flutter_app/lib/data/kind_fields.dart` — зеркало серверной таблицы:
перечисление `ListingField`, константа `kindFields` и хелпер
`bool showsField(PropertyKind kind, ListingField field)`. К нему обращаются
форма, фильтр и карточка, чтобы правило не расползлось по экранам.

### Форма подачи

`ui/pages/ad_form_page.dart` — обычный `Column`, каждая секция уже отделена
`_buildSectionTitle`, поэтому изменения точечные:

- секции «Комнаты», «Этаж», «Этажность», «Серия», «Застройщик» оборачиваются в
  проверку `showsField`;
- добавляются секции «Назначение участка», «Назначение помещения», «Отдельный
  вход», «Линия», «Высота потолков» — теми же `_buildChip` и `_buildInputField`,
  что и остальные, поэтому визуально неотличимы от существующих;
- при смене типа значения скрытых полей сбрасываются в черновике, иначе на
  сервер уедет `rooms` от предыдущего выбора.

### Карточка и превью

- `ui/object_card.dart:178` — условия `rooms > 0` / `floor > 0` заменяются
  проверкой по типу; для участка вместо комнат показывается площадь участка.
- `ui/pages/listing_page.dart:651` — убирается зашитый фолбэк
  `floors > 0 ? floors : 12`, рисующий «этаж из 12» там, где этажей нет; блок
  характеристик собирается из применимых полей.
- `ui/pages/ad_preview_page.dart:406` — `${item.rooms}-комн.` и
  `${item.floor}/${item.floors} эт.` становятся условными.

### Фильтр

`ui/pages/filter_page.dart` сейчас не список, а кадр Figma: чипы комнат стоят на
жёстких координатах (`_roomChips`), цена — на `top: 475`, тумблеры продавца — на
своих `y`. Спрятать блок = оставить дыру.

Экран пересобирается как прокручиваемый столбец секций с переиспользованием тех
же `FigChip`, `FigToggle`, `FigInputBox` — чипы, шрифты, цвета и отступы
остаются прежними, меняется только способ расстановки. Появляется прокрутка,
которой сейчас нет: новые фильтры коммерции в фиксированный кадр не помещаются.

Секции фильтра показываются, если применимы **хотя бы к одному** из выбранных
типов; когда не выбран ни один тип, показываются все секции.

## Тестирование

Бэкенд (`pytest`):

- `field_rules`: `strip_inapplicable` убирает `rooms` для участка и сохраняет
  его для квартиры;
- публикация участка без `rooms`/`floor` проходит, публикация квартиры без них —
  нет, с перечислением в `missing_fields`;
- PATCH черновика участка с `rooms=3` возвращает 200, и в базе `rooms` не
  изменился;
- фильтрация по `commercial_purpose` возвращает только коммерцию;
- снапшот OpenAPI обновлён через `make schema-update` и контрактный тест
  проходит.

Клиент: `dart analyze lib` без ошибок; ручная проверка формы для всех шести
типов и фильтра с выбранным типом «Участки».

## Что осознанно не делается

- Динамическая схема формы с сервера — обсуждалась как вариант B и отклонена.
- Чистка исторических значений в существующих объявлениях.
- Высота потолков как обязательное поле — по условию всегда необязательна.
- Новые типы недвижимости: список из шести значений зафиксирован в ТЗ.
