# Переписка по объявлению — дизайн

## Цель

Добавить в House KGZ встроенную переписку покупателя с продавцом по конкретному
объявлению и рабочую кнопку звонка. Первый релиз должен быть полезным сам по себе,
не перегружать текущий сервер и позволять позднее добавить WebSocket, вложения и
расширенную модерацию без переделки базы данных и Flutter-интерфейсов.

## Объём первого релиза

В релиз входят:

- создание или открытие диалога с продавцом из активного объявления;
- список диалогов пользователя со счётчиками непрочитанных сообщений;
- отправка и чтение текстовых сообщений длиной до 2000 символов;
- защита от повторной отправки сообщения при нестабильной сети;
- отметка прочтения;
- уведомление получателя о новом сообщении;
- защищённое раскрытие номера и запуск системного приложения для звонка;
- сохранение карточки объявления в диалоге после архивации или удаления объявления;
- REST-обновление открытого чата с возможностью последующей замены транспорта на WebSocket.

В релиз не входят фото, видео, файлы, голосовые сообщения, редактирование и удаление
сообщений, онлайн-статус, индикатор набора, блокировка пользователей и WebSocket.

## Пользовательский сценарий

На странице объявления постоянно доступна нижняя панель с основной кнопкой
«Написать» и вторичной кнопкой звонка. Автор объявления вместо этих действий видит
нейтральное состояние без возможности начать диалог с самим собой.

Если гость нажимает «Написать» или «Позвонить», приложение открывает вход и сохраняет
намерение. После успешной авторизации пользователь возвращается к объявлению, а
действие продолжается. Авторизованный покупатель по кнопке «Написать» идемпотентно
создаёт или получает существующий диалог и переходит в чат.

Экран чата содержит компактную карточку объявления, имя и аватар собеседника, историю
сообщений и поле ввода. Новые сообщения появляются без перезагрузки экрана. Экран
«Сообщения» доступен из профиля и показывает карточки диалогов: собеседника, объявление,
последнее сообщение, время и число непрочитанных.

## Архитектура backend

Создаётся отдельное Django-приложение `apps.messaging`. Представления отвечают только
за HTTP-контракт; права, транзакции, создание диалогов, отправка и прочтение сообщений
реализуются в `services.py`, а выборки с `select_related` и аннотациями — в
`selectors.py`.

### Conversation

- `id`: UUID, публичный идентификатор;
- `listing`: nullable FK на объявление с `SET_NULL`;
- `buyer` и `seller`: FK на пользователей;
- `listing_slug`, `listing_title`, `listing_price`, `listing_currency`,
  `listing_cover_url`: снимок карточки при создании;
- `last_message_at`: время сортировки списка диалогов;
- `buyer_last_read_at`, `seller_last_read_at`: отметки чтения участниками;
- `created_at`, `updated_at`.

Ограничение уникальности `(listing, buyer, seller)` не допускает два диалога по одному
объявлению. Создание выполняется внутри транзакции и корректно обрабатывает гонку.
Диалог может быть создан только для доступного активного объявления, покупатель не
может быть его владельцем. Уже созданная переписка остаётся доступной после изменения
статуса объявления.

### Message

- `id`: UUID, публичный идентификатор;
- `conversation`: FK;
- `sender`: FK на пользователя;
- `text`: строка после `trim`, от 1 до 2000 символов;
- `client_message_id`: UUID, который генерирует Flutter;
- `created_at`.

Ограничение уникальности `(sender, client_message_id)` превращает повторный POST после
таймаута в безопасное получение уже созданного сообщения. Отдельный `read_at` на каждом
сообщении не нужен: прочтение вычисляется по отметке участника в диалоге.

## REST API

Все маршруты требуют JWT и находятся под `/api/v1/`.

### `POST /conversations/`

Запрос:

```json
{"listing_slug": "3-komnatnaya-kvartira-v-centre"}
```

Возвращает созданный или существующий диалог. Для нового ресурса используется `201`,
для существующего — `200`. Ошибки: `404` для недоступного объявления, `409` при попытке
написать самому себе.

### `GET /conversations/`

Курсорный список диалогов текущего пользователя, отсортированный по
`last_message_at DESC`. Элемент содержит снимок объявления, собеседника, последнее
сообщение и `unread_count`. Запрос не должен создавать N+1.

### `GET /conversations/{id}/`

Возвращает диалог только его участнику. Чужой UUID отвечает `404`, чтобы не раскрывать
существование переписки.

### `GET /conversations/{id}/messages/`

Курсорная история сообщений. Начальная страница возвращает последние сообщения;
параметр `after=<message_uuid>` позволяет открытому чату получить только новые.

### `POST /conversations/{id}/messages/`

Запрос:

```json
{
  "text": "Здравствуйте! Когда можно посмотреть квартиру?",
  "client_message_id": "ec4a6dd2-7bbc-4be4-b231-80fce83eeb67"
}
```

Отправитель обязан быть участником диалога. Повтор с тем же
`client_message_id` возвращает исходное сообщение и не создаёт уведомление повторно.
После создания атомарно обновляется `last_message_at`.

### `POST /conversations/{id}/read/`

Запрос содержит `last_message_id`. Backend сдвигает отметку чтения только вперёд и не
помечает прочитанными сообщения, пришедшие позже указанного. Ответ содержит актуальный
`unread_count`.

### Контакт продавца

Звонок использует существующий `POST /listings/{slug}/contact/`. Flutter не хранит
полный телефон из публичного ответа объявления: получает его после явного нажатия,
затем запускает URI `tel:`. Это сохраняет текущую аналитику раскрытия контакта.

## Обновление сообщений и будущий realtime

Открытый чат делает лёгкий запрос `messages/?after=<last_message_uuid>` каждые пять
секунд, только пока приложение активно и экран видим. При уходе со страницы таймер
останавливается. Отправленное сообщение сразу отображается в состоянии `sending`, а
ответ API переводит его в `sent`; ошибка даёт повторить отправку с тем же UUID.

В будущем WebSocket будет передавать тот же сериализованный объект сообщения. Модели,
экран и локальный контроллер не зависят от транспорта, поэтому меняется только источник
событий.

## Уведомления

В `NotificationType` добавляется `NEW_MESSAGE`. После первого создания сообщения
получателю создаётся уведомление с `conversation_id`, снимком объявления и идентификатором
отправителя. Отправителю уведомление не создаётся. Существующий push-механизм используется
как best effort: сбой push не откатывает сохранённое сообщение.

Нажатие уведомления открывает нужный чат. В настройках появляется отдельный флаг
уведомлений о сообщениях, включённый по умолчанию.

## Flutter-компоненты

- модели `ConversationSummary`, `ChatMessage`, `ChatPeer` отделены от UI;
- `MessagingRepository` инкапсулирует REST-контракт;
- `ChatController` отвечает за загрузку, polling, optimistic-send, повтор и read receipt;
- `MessagesPage` показывает список диалогов и состояния loading/empty/error;
- `ChatPage` отображает карточку объявления, сообщения и composer;
- `ListingContactBar` переиспользуется на странице объявления и в просмотре фото/видео,
  где контактное действие уместно;
- маршруты принимают типизированные аргументы, а не неструктурированные Map.

Дизайн использует текущие цвета, типографику и размеры House KGZ. Поле ввода учитывает
клавиатуру и safe area; кнопка отправки недоступна для пустого текста. Длинные сообщения
переносятся, системный размер шрифта не вызывает overflow.

## Безопасность и ошибки

- все endpoint'ы используют `IsAuthenticated`;
- queryset всегда ограничен участником диалога;
- текст отображается как обычный Flutter `Text`, без HTML;
- отправка ограничена отдельным DRF throttle, базово 30 сообщений в минуту;
- содержимое сообщений и полные телефоны не пишутся в application-логи;
- невалидный текст отвечает единым `validation_error`;
- отсутствие сети сохраняет неотправленное сообщение на экране с действием «Повторить»;
- `401` запускает существующий сценарий повторной авторизации;
- удаление аккаунта удаляет его диалоги и сообщения согласно текущей политике удаления
  персональных данных.

## Тестирование

Backend-тесты покрывают права обоих участников и постороннего пользователя, создание
и повторное открытие диалога, запрет self-chat, гонку создания, идемпотентную отправку,
валидацию текста, unread/read, сортировку, пагинацию, отсутствие N+1, уведомление и
доступ к переписке после архивации объявления.

Flutter-тесты покрывают сериализацию, API-запросы, возврат после авторизации,
optimistic-send и retry с тем же UUID, polling lifecycle, пустой/error UI, клавиатуру,
переполнение текста и переходы со страницы объявления, профиля и уведомления.

## Развёртывание

Изменения выполняются локально через TDD. Backend и Flutter коммитятся в соответствующие
репозитории и отправляются в GitHub. На сервере выполняются `git pull`, установка только
зафиксированных зависимостей при их появлении, `manage.py migrate`, `manage.py check`,
целевые и интеграционные тесты, затем безопасный перезапуск Gunicorn и smoke-проверка API.
Миграция только создаёт новые таблицы и поля уведомлений и не изменяет существующие
объявления или пользовательские данные.
