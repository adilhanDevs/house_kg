# Поля, которых нет в форме приложения

Дата: 2026-08-31

## Проблема

Часть полей объявления заполняется только через админку Django. Аудит (сверка
`ListingUpdateSerializer.Meta.fields` с тем, что реально отправляют экраны
`ad_*`) вскрыл три разные проблемы.

**1. Поля, которые нельзя ввести ниоткуда из приложения.** API их принимает, ни
один экран не отправляет: `landmarks`, `contact_name`, `contact_phone`,
`is_secondary`, `has_direct_sale`, `has_mortgage`, `latitude`, `longitude` и
семь площадей комнат (`living_room_area`, `hall_area`, `kitchen_area`,
`bedroom_area`, `bedroom_2_area`, `balcony_area`, `bathroom_area`). Площади
комнат при этом показываются на детальной странице — значениями по умолчанию,
то есть выдуманными.

**2. Формы создания и редактирования разошлись.** `address`, `description`,
`furniture`, `series` есть в `ad_edit_page.dart`, но их нет в `ad_form_page.dart`:
при создании объявления адрес и описание ввести невозможно.

**3. Молчаливая потеря данных.** `ad_edit_page` отправляет шесть полей, которых
в API не существует: `floors_total`, `condition`, `heating`, `has_gas`,
`mortgage_ready`, `exchange_possible`. DRF игнорирует неизвестные ключи, запрос
возвращает 200, данные исчезают. Хуже всего `floors_total`: этажность при
редактировании не сохранялась никогда, потому что поле называется `floors`.

Отдельно: `furniture` в модели — свободный текст с русским значением по
умолчанию («Полностью»), а интерфейс шлёт туда коды `full` / `partial` / `none`.

## Решения, принятые при обсуждении

- Фантомные поля (`condition`, `heating`, `has_gas`, `exchange_possible`)
  заводятся в модели, а не выкидываются из интерфейса.
- `mortgage_ready` — это существующий `has_mortgage`, новое поле не нужно.
- Координаты (`latitude`, `longitude`) откладываются: нормальный ввод — это
  карта с меткой, картографической библиотеки в проекте нет, и эта задача
  затмила бы остальное.
- Необязательные поля в форме создания прячутся под раскрывающиеся блоки
  (вариант A), а не выносятся в новый шаг мастера и не вываливаются плоским
  списком.
- Сборка payload выносится в общий модуль, чтобы формы создания и
  редактирования не могли разъехаться повторно.

## Бэкенд

### Новые поля `Listing`

Коды значений берутся ровно те, что уже использует интерфейс редактирования —
клиент переучивать не нужно.

| Поле | Тип | Значения |
|---|---|---|
| `condition` | `CharField(choices, blank=True)` | `euro`, `good`, `shell`, `medium`, `none` |
| `heating` | `CharField(choices, blank=True)` | `central`, `gas`, `electric`, `autonomous` |
| `has_gas` | `BooleanField(default=False)` | — |
| `exchange_possible` | `BooleanField(default=False)` | — |

Перечисления `ListingCondition`, `HeatingKind`, `FurnitureKind` — в
`apps/catalog/enums.py`.

### `furniture` переводится в choices

`full` · `partial` · `none`, `blank=True`. Миграция данных переносит
существующие значения: «Полностью» → `full`, «Частично» → `partial`, остальное
(включая пустое) → `""`. Без неё старые записи показывали бы русский текст там,
где интерфейс ждёт код.

### Остальное

- Новые поля добавляются в `ListingUpdateSerializer`, `ListingDetailSerializer`,
  админку и `field_rules.KIND_FIELDS`: `condition`, `heating`, `has_gas` — к
  типам с внутренними помещениями (квартира, комната, дом, новостройка),
  `exchange_possible` — ко всем типам.
- `landmarks`, `contact_name`, `contact_phone`, `address` и площади комнат в
  сериализаторах уже есть — там менять нечего.
- Снапшот OpenAPI пересобирается через `make schema-update`.

## Клиент

### Общий модуль payload

`flutter_app/lib/data/listing_payload.dart` — одна функция
`Map<String, dynamic> buildListingPayload({...})`, собирающая тело запроса из
переданных значений с учётом `kind_fields.dart`. Обе формы вызывают её со
своими значениями; вёрстка у каждого экрана остаётся своя.

Ключи payload проверяются тестом против списка полей
`ListingUpdateSerializer` — именно отсутствие такой проверки позволило
`floors_total` тихо жить в коде.

### Форма создания

`ad_form_page.dart` получает три раскрывающихся блока после обязательных
секций, свёрнутых по умолчанию:

- **«Подробнее об объекте»** — адрес, описание, мебель, состояние, отопление,
  газ, вторичка, возможен обмен, прямая покупка, ипотека, серия дома;
- **«Площади комнат»** — семь полей, показывается только для типов с
  `ListingField.interior`;
- **«Контакты и ключевые места»** — имя и телефон контакта, список ключевых мест
  с добавлением и удалением.

Внутри блоков — те же `_buildSectionTitle`, `_buildChip`, `_buildInputField`,
`_buildToggleRow`, что и в остальной форме.

### Форма редактирования

- `floors_total` → `floors`, `mortgage_ready` → `has_mortgage`;
- `condition`, `heating`, `has_gas`, `exchange_possible` теперь сохраняются;
- убирается подстановка «первой попавшейся серии из справочника», когда
  введённая не нашлась: это тихо подменяет данные пользователя;
- сборка payload заменяется вызовом общего модуля.

## Тестирование

- PATCH черновика с адресом, описанием, ключевыми местами, контактами и
  площадями комнат сохраняет их все;
- PATCH с `condition`, `heating`, `has_gas`, `exchange_possible` сохраняет их;
- миграция `furniture` переносит «Полностью» в `full`;
- каждый ключ из `buildListingPayload` присутствует в
  `ListingUpdateSerializer.Meta.fields`;
- `dart analyze lib` без ошибок.

## Что осознанно не делается

- Карта и координаты объекта.
- Объединение экранов создания и редактирования в один: общим делается только
  сборка payload, вёрстка остаётся раздельной.
- Приведение `landmarks` к справочнику — остаётся свободным списком строк, как
  в модели.
